# 双 README 文档设计

## 目标

为项目补充两份用途明确、内容一致的入口文档：根目录 `README.txt` 用于题目要求的最终提交包，根目录 `README.md` 用于公开 GitHub 仓库。两份文档均使用中文，以“从模糊的需求到可靠的软件”为项目口号，准确说明已经实现的能力，不使用无法验证的比较或宣传表述。

## 核心叙事

nano-vibe-coder 的核心创新是把软件工程智能体建模为有限状态机，通过 `REQUIREMENTS → PLAN → IMPLEMENT → VERIFY → DONE` 五个阶段约束模型行为。相较于主要围绕规划和编码循环工作的 Coding Agent，本项目将需求分析和软件验证建模为独立阶段：修改代码前先理解用户目标，完成实现后再通过计划门槛、验证结果和项目规范审查确认交付质量。

文档需要说明状态机与应用层权限策略是两个不同维度。阶段决定模型当前可以使用哪些工具；Normal 与 Full Access 决定受限工具是否需要应用层审批。Full Access 不绕过阶段白名单、工具参数校验、工作区路径校验或 DONE 门槛，也不等同于操作系统沙箱。

## README.txt

`README.txt` 控制在 1000 个字符以内，目标长度约为 700 至 850 个字符。采用纯文本小标题和紧凑段落，包含题目明确要求的以下信息：

1. 项目名称、口号和一句话定位。
2. 公开 Git 仓库地址。
3. 核心创新与五阶段流程。
4. CLI 和 GUI 的最短安装、配置及运行命令。
5. 可观察 GUI、结构化计划、权限审批、Session 恢复和本地工具等功能亮点。
6. 本地运行、安全边界和配置文件不提交 Git 等必要说明。

文档不重复详细架构，也不加入尚未确定的视频地址。字符数在提交前使用 `wc -m` 验证，并为不同平台对换行符的计数差异保留余量。

## README.md

`README.md` 面向评审者和实际使用者，按照“项目价值 → 设计创新 → 快速运行 → 技术细节”的阅读顺序组织：

1. 标题、口号、一句话介绍和项目状态。
2. 项目动机，以及为什么独立设置 REQUIREMENTS 和 VERIFY。
3. 五阶段状态机、转换门槛及与常见 Coding Agent 的设计差异。
4. 功能亮点，包括计划、工具、GUI、权限、Session、Trace 和上下文管理。
5. CLI 与 GUI 快速开始、配置示例和常用命令。
6. 各阶段工具权限，以及 Normal / Full Access 的安全语义。
7. Plan、Diff、Trace 的可观察性和 Session 恢复机制。
8. 主要源码目录、运行架构和数据存放位置。
9. 开发检查、联网测试、当前限制和第三方声明。

功能对比只描述架构差异，不声称对所有其他产品具有绝对优势。运行命令必须与当前 CLI、`config.example.toml` 和前端构建方式一致；配置示例不得包含真实密钥。没有仓库内可长期访问的截图资源时，不添加失效的图片链接。

## 一致性与验证

两份文档使用相同的项目定位、状态名称、权限语义和运行命令。实现后检查：

- GitHub 地址与 `origin` 一致。
- `README.txt` 总字符数不超过 1000。
- CLI 与 GUI 帮助命令能够运行。
- 文档未泄露 `config.toml`、环境变量或真实 API key。
- Markdown 链接和仓库内文件路径有效。
- `git diff --check` 通过，并检查完整 diff 后再提交。

## 非目标

- 不修改代码、配置、依赖或前端界面。
- 不制作截图、徽章、演示视频或英文版本。
- 不为尚未实现的能力编写路线图式承诺。
- 不把 Full Access 描述为操作系统级安全隔离。
